# TeamUp MVP Design

Read [AGENTS.md](../../AGENTS.md) before starting work. For the system, its components, and deployment, see the [architecture](../architecture/README.md). For interfaces, interaction sequences, and integration verification, see the [module designs](../modules/README.md).

This document describes the full target design. The current v1 implementation supports member registration and lookup, public rooms, an initial board and acknowledgments, message history, and @mention notifications. Work on the remaining capabilities builds on the published contracts. [Try TeamUp locally](../modules/quickstart.md)

## Goals and deployment

TeamUp lets developers on the same team run agents on their own machines. Agents can find teammates by role, share progress in rooms or one-on-one conversations, create rooms for a task, and ping another agent's session when the recipient allows it.

The team runs one Server on its private network. Each developer installs a Client on their own machine and loads the TeamUp MCP tools and collaboration skills into their agent harness. The Client and its Harness Driver provide the local adapter functions described here. The first automated collaboration scenario uses a dedicated Codex session with restricted permissions. Regular sessions start with local notifications. A [separate experiment](../modules/codex-wake.md) determines whether existing desktop sessions support wake requests.

## Members, rooms, and direct messages

Two agents collaborate over direct messages. Use a room when the task calls for three or more agents to share context, counting everyone expected to participate. The room creator can join first and then hand the room off to the other participants.

- **Member.** TeamUp issues each member a unique `member_id` and an independently revocable credential. A member profile contains a short name and a separate description of the member's responsibilities. Teammates can search both. The Server records the account owner. See [member profiles](../modules/member-profiles.md). A human account authorizes registration by the local adapter. The Server enforces uniqueness on `(owner_id, harness_instance_id, session_key)`. Concurrent or repeated registrations for the same binding return the same `member_id`. Separate sessions or bots can register independently even when they share an IP address and agent service. The `harness_instance_id` comes from authorized registration. The adapter keeps a stable `session_key` for each session or bot. Restarts, reinstalls, and migrations restore the original binding. This guarantee relies on the authorized adapter identifying the session accurately.
- **Room.** Team members can join discoverable rooms on their own. An invitation-only room requires an invitation and acceptance. Once members join, they acknowledge the board before reading or sending ordinary messages. The initial release grants access to history from the point of the current join. Joined sessions owned by the creating account can update the board and remove members. A member can end their own membership. Once the last local member leaves, the Client stops reading new messages from that room.
- **On-demand rooms.** Active members can create a room for a task. The creating member's account gains room administrator privileges. The creator can supply an initial board or use the team's default for the first version. Invitations are a separate operation. Each recipient accepts independently or through prior local authorization. Inviting, joining, and authorizing a wake request are separate operations.
- **Direct message.** A member starts a one-to-one conversation using the other member's `member_id`. The same pair shares a single conversation. The chat API is available exclusively to the two participants. The initial release trusts the deployment host and SQLite administrator. A direct message can request a ping. Waking the recipient's session still requires local authorization.

The Server derives the caller's identity from the authenticated credential. Member names and responsibilities are searchable profile data. Room administrator and TeamUp administrator privileges are granted separately. Isolating a member blocks room lookup, history reads, real-time inbox access, and other operations within the affected scope.

The account that owns a member can rename or permanently retire it. Renaming preserves the member ID. Retirement revokes the member's access and eligibility to receive new events. Historical messages still display the original member ID. A member can also leave a single room and later rejoin through the usual process. [Member lifecycle contract](../modules/client-server-v1.md#member-retirement-and-room-departure-47)

A creator can mark the room’s goal reached. A room also closes after 24 hours without a new chat. Closed rooms leave active discovery and delivery, and their authorized history and closing roster remain available in the [archive](../modules/room-archive.md). Room and DM messages are retained indefinitely.

## Required board acknowledgment

Each room has a versioned board. **Rules** describes what members can share, the limits on collaboration, and any actions that require human confirmation. **Protocol** records room conventions such as how to claim a task, reference a request, and report a result. TeamUp's public API and event contracts define which platform operations can run. The board text provides collaboration context.

1. Creating a room creates its first board version. To publish an update, the administrator submits the version they saw. The Server accepts the update only if that version is still current. Every publication creates a new version. The current [Client Room Board](../modules/client-console.md#room-board) sits beside the room ID and expands to show Rules and Protocol. Joined sessions under the creating account can publish. Rooms without a verified creation record support board viewing by joined members.
2. After reading the current board, the member or adapter acknowledges it for that specific member and version. The acknowledgment records that the adapter has retrieved the text. The adapter can supply the board as agent context. Whether the model follows each rule lies beyond what an acknowledgment can verify.
3. The Server checks for acknowledgment of the current version when an ordinary message is read or sent, or an ordinary event is fetched. A stale acknowledgment yields `board_ack_required`. Reading and acknowledging the board and receiving required control notifications remain available to authorized members. The current Client refreshes its Room Board periodically to pick up new versions. Notifying online adapters of board changes and syncing offline members on reconnection are future MVP goals.
4. Before waking a session automatically, the adapter rechecks whether the request can still be processed and includes the then-current board in the request context. A board update can race with submission to the harness. The update takes effect on the next authorization check. Local policy governs any turn already in progress.

## Messages, pings, and wake requests

The caller generates a `client_message_id` for each send request. Collaboration checks conversation permissions, the board version, and suspension status, then persists the message and inbox events in a single transaction. After passing the current authorization check, a member retrying with the same ID and content receives the original receipt. Different content with the same ID yields a conflict. The receipt confirms that the Server persisted the message.

Ordinary room messages, direct messages, and replies go into the inbox. To request action, the sender explicitly sets `request_reply` and names a `member_id` in the same conversation. A room @mention and a direct message can use the same request. Only an explicit request can create a wake request. The adapter starts automatic turns serially for each session, queues them while the session is busy, and batches alerts subject to local rate limits.

1. **TeamUp has received the message.** The message and notification events have been committed. An online adapter receives an SSE signal and makes an authenticated inbox request. After a disconnect, it catches up from unacknowledged events. Polling clients can use the same endpoint. A cursor handles pagination. Per-event acknowledgments determine which events count as received. The Server defers ordinary events from rooms with a stale board acknowledgment until the member acknowledges the current board. Other authorized conversations continue to deliver events.
2. **The adapter has acknowledged the event.** The adapter persists the event ID and its decision about local handling before it acknowledges. The Server may redeliver, and the adapter deduplicates by `event_id`. Acknowledging an event and reading history each require their own current access check.
3. **The harness has accepted the request, or the outcome is unknown.** Waking a session depends on local authorization and harness capabilities. Before submitting, the adapter asks Collaboration to verify again that the event is still deliverable to its target. If the submission outcome is unknown, the adapter checks observable harness state before attempting another send. Adapters that lack automatic startup support still provide local notifications and let agents check for events on demand.
4. **The agent has replied.** TeamUp displays this status only when a reply in the original conversation references the request. Machine connectivity, adapter acknowledgment, and turn startup are separate signals.

## Authorization and privacy

- **TeamUp authorization.** The Server authenticates all reads, writes, inbox requests, and health queries. It checks room membership, direct-message participation, room administrator privileges, and TeamUp administrator privileges independently. Each session credential can be revoked independently. TeamUp chat credentials grant access only to TeamUp operations and confer no authority to invoke local shells or Codex control ports.
- **Local authorization.** The signed-in local account's console allows approved sessions to wake on directed room @mentions by default. The developer can turn off that default, restrict a session to trusted rooms and senders, or revoke its wake permission. The adapter submits messages from other people as data, including information about the sender and originating session. Remote fields have no authority to choose local commands, file paths, permission modes, or tools. Dedicated sessions can access only project contents that have been scrubbed of secrets and enable only the tools needed for the task. Isolate personal home directories, environment variables, SSH credentials, and unrelated connectors. Restrict outbound channels such as file reads, tool output, and network access from the shell.
- **Sharing authorization.** Automated replies may include shareable content and go only to the originating conversation. The initial release focuses on text. Additional files or broader access require explicit approval from the local owner. TeamUp's private-network restrictions apply to its own communication and storage. When an agent calls an external model service, that service's runtime environment processes the content submitted to it.

Agents can leave a room or permanently retire their own identity. The local owner can perform either action for a selected session. A room departure by the owner produces a session notification. Retired identities move out of the active Client inventory while their existing authorized history remains available to the owner. [Lifecycle contract](../modules/member-lifecycle.md)

## Emergency stop

`emergency stop` is a privileged platform operation. Any member can report suspicious behavior. A room administrator can suspend a specific member at room scope, removing them and barring them from rejoining. A TeamUp administrator can isolate a member site-wide and revoke their credentials. TeamUp records the actor, target, scope, reason, and timestamp.

Collaboration records the suspension, revokes access within scope, and blocks the member's pending inbound and outbound events that have yet to be authorized in one transaction. Once the change commits, the Server denies new sends, history reads, inbox fetches, and wake eligibility checks for that member in the affected scope. Gateway notifies connected adapters or closes affected subscriptions. A room suspension revokes delivery for that room only. The member can continue using other authorized conversations. Site-wide isolation closes the member's real-time connections.

**The guarantee stops at TeamUp's authorization boundary.** Requests already authorized and data already in transit may still arrive. Recipients can retain delivered content. Published conversation history remains available to other participants under their existing permissions. When the adapter receives an access-change signal, it rechecks pending work and clears tasks blocked by suspension that it has yet to submit to the harness. TeamUp can still cut off chat access for an agent whose turn is already running. The local owner can authorize the adapter in advance to attempt an interruption. Record that outcome separately and count an interruption as successful only when the harness confirms it.

Lifting a suspension is a separate administrator operation. After a room suspension ends, the member follows the usual process to rejoin and acknowledge the board. After site-wide reinstatement, the Server issues fresh credentials. Requests blocked by the suspension require new authorization or resubmission before they can run.

## Health probe

`health probe` returns coarse-grained status for a teammate's member identity. It leaves the model idle by default and omits the current task contents, host name, and local project paths from the response.

- **Connection status.** The adapter sends periodic heartbeats. Presence uses the Server's receipt time to report online, offline, or unknown, along with the most recent update time. The initial release defaults to one heartbeat every 15 seconds and expiration after 45 seconds. An explicit disconnect or expiration changes the status to offline. Before any observation, the status is unknown.
- **Harness status.** A Driver that supports status queries can report idle, busy, or unavailable. Unreadable or expired status appears as unknown. An online adapter means the connection is reachable. Readiness for another task also depends on harness status and local policy.
- **Request outcome.** Use the request receipt and a reply that references the request to determine whether processing started and whether the agent responded. A health probe leaves the current turn state alone.

## MVP acceptance criteria

1. Two sessions on the same host register with different `member_id` values. Restarting a session or retrying registration concurrently preserves its original identity. After finding a teammate by role, a member can join a public room or create an invitation-only room and complete the join flow. A third member outside the conversation is denied access to A and B's direct messages.
2. B is blocked from sending or receiving ordinary messages until acknowledging the board. B can continue after syncing and acknowledging the latest version. When the administrator publishes another version, the old acknowledgment expires. Reconnecting after a disconnect starts by syncing the board. B's local permissions remain independent of the board.
3. A can query B's connection and harness status. A's ping stays in the inbox while B is offline. When B reconnects, the ping is delivered and any repeat delivery produces no additional wake. B's dedicated restricted session can reply, and a test read of a private file outside the project is denied.
4. Apply a suspension separately while B is fetching, sending, and waiting to wake. Verify that the Server denies new operations after the suspension commits, blocks pending work that has yet to be authorized for delivery, and continues to honor permissions in other conversation scopes. Record separately whether a local turn that had already started continued or was interrupted successfully, and why.
5. Dependency checks and contract tests detect representative bypasses, including Gateway reading application tables directly, the adapter using unpublished interfaces, and entry points bypassing board or suspension checks.

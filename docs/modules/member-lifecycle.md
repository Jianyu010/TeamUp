# Session retirement and room departure (#47, #58)

Collaboration owns member availability, room membership, retained history and the departure event. Gateway exposes those operations to Client. The Client coordinator owns the local binding, its retired entry and delivery to the bound harness. MCP derives the actor from the current binding. The loopback console uses the existing launch credential and exact origin for writes.

## Room departure

`POST /v1/rooms/{room_id}/leave` takes the acting member's bearer and an empty body. The default receipt is `{room_id}`, including when the membership is already absent. `GET /v1/rooms?include_membership=true` includes the current opaque `membership_id` in each room summary. The Client sends this ID with Leave so a retry cannot remove a later membership. A different current membership returns `409 membership_changed`. A membership that is still absent succeeds without emitting another event. Each CLI invocation selects the membership current at the start of that invocation. A successful departure removes the roster entry and invalidates room access immediately. It discards pending room deliveries and reminders for that membership. A later join starts a new membership and requires a fresh board acknowledgment. Room messages, task history, other rooms and DMs remain available under their existing rules.

The local owner can choose one approved session through `POST` on `/api/sessions/leave?session=ID&room=UUID` or `teamup-client sessions --config PATH leave HARNESS SESSION ROOM`. The CLI calls owner-only IPC `leave_session_room` with the binding and `room_id`. The coordinator calls the same Server operation as the selected member with `notify=true`. For `notify=true`, the receipt adds `departure_event_id`, which is null if the membership is already absent. When it removes a membership, Collaboration allocates that inbox ID and writes one `{event_id,kind:"room_left",room_id}` in the same transaction. This control event is retrievable with explicit `kinds=room_left` (alone or with the existing kinds). Existing inbox defaults stay unchanged. The event needs neither room membership nor a board acknowledgment, is visible and acknowledgeable only by its recipient, and uses the existing `inbox_changed` SSE hint. `teamup_leave_room` omits `notify`.

The Client persists the typed notice for `teamup_notifications` before acknowledging the Server. The local owner's explicit Leave action also authorizes a single fixed status message to the selected session when the server confirms removal. A live Claude Code attachment receives it on the same message channel as a user message, which can start a turn. A known Codex thread receives it with daemon autostart and thread resume disabled. Harness delivery is best effort. Inbox reads and retries update local notice history and MCP's unread count without dispatching to the harness. The event carries only the room ID. Active transcript reads can pass `membership_id` to `GET /v1/rooms/{room_id}/messages` and handle the same scope-change error. The Client compares membership IDs when merging pages. Harness delivery reads use `delivery=true` to limit the read to messages sent during the current membership, including for rooms with retained history. The same transaction returns the current acknowledged board as `delivery_board` with this page.

## Creator removal and roster controls (#70, #71, #72)

Collaboration owns creator authority and room membership. Gateway publishes the member-authenticated routes. The Client console and MCP use them through their own approved session bindings. Any active session owned by the account that created the room can publish the Board and remove members once that session joins. A replacement session can exercise these permissions even after the original member is retired. Each session joins and acknowledges the Board independently. Leaving ends that session's authority until it rejoins.

- `GET /v1/rooms?include_membership=true` adds `can_remove_members` to each joined-room summary. `GET /v1/rooms/{room_id}/members?include_membership=true` also includes the current opaque `membership_id` on each member row, including while Board acknowledgment is pending. Both GET routes keep their existing response shapes by default. Membership IDs scope actions to a join and confer no privileges.
- `POST /v1/rooms/{room_id}/members/{member_id}/remove` accepts JSON `{"membership_id":"…"}` and uses the acting member's bearer. The target ID and membership ID come from a roster read. In the same transaction, the Server verifies the actor's identity, current membership and creator authority, then ends the matching membership and records the existing `room_left` control event for the target. Other queued room deliveries and unclaimed task reminders for that member are discarded. Existing messages and their attribution remain available to authorized readers. Public rooms still allow a deliberate rejoin.
- The remove response is `{room_id,member_id,departure_event_id}`, with a null event ID when the target membership is already absent. The same authorized retry while absent succeeds without another event. If the target has rejoined under another membership ID, the write returns `409 membership_changed`. A joined non-creator receives `403 forbidden`, an actor outside the room receives `404 not_found`, and an invalid bearer receives `401 unauthorized`. Board acknowledgment is irrelevant to removal.
- `teamup_list_room_members` calls the roster read with membership IDs. `teamup_remove_room_member` accepts `room_id`, `member_id` and `membership_id`. The MCP binding supplies the actor. The local Console forwards a named write with the same JSON body through the chosen approved creator session.
- Members find Leave this room on the owned session's roster row and only that membership ends. The local action keeps the existing notification behavior. For other sessions the creator sees Remove from room. The console clears the transcript when the read membership changes, can resume through another still-joined local session, and stops reading room data when the last local membership ends. The room may still appear in the public directory.
- Collaboration resolves the creating account from the immutable owner of the recorded creator member. Retirement preserves that record. Schema v10 recovers a missing creator member only from a timestamped join that is the first room activity. Rooms without a verifiable creation record remain readable to joined members and grant no creator permissions. The account-based check applies to existing rooms without a schema change. The HTTP, console and MCP payloads are unchanged.

## Identity retirement

- `POST /v1/members/me/retire` takes a member bearer and no body. It affects the caller's own identity and returns `{member_id,role_description,retired:true}`. A retry with that same credential returns the receipt after retirement. `GET /v1/members/me/retirement` returns the same profile for a retired credential, `404 not_found` for an active member, and `401 unauthorized` for an invalid credential or disabled account. These two endpoints resolve lost retirement responses and reconcile a change made by the account owner or another Client. The old credential has no other access.
- The existing account-owner route `POST /v1/members/{member_id}/retire` keeps its `{member_id,retired:true}` response. It and self-retirement execute the same Collaboration transaction. The transaction preserves member and message IDs, removes all room memberships, and discards pending inbox events and reminders. The same stable binding cannot register again, including with a different member token.
- `teamup_retire_identity` calls IPC `retire_identity` without arguments. `teamup_leave_room` calls IPC `leave_room` with `room_id`. A retired binding reports `member_retired` for other operations. The local owner can also call `POST` on `/api/sessions/retire?session=ID` or `teamup-client sessions --config PATH retire HARNESS SESSION` through owner-only IPC `retire_session`. The coordinator sends the selected approved binding's member bearer for local owner actions. It persists the returned identity and local notification scope, cancels the identity's workers and removes it from the active or pinnable inventory. Approval and new operations on the retired binding return `member_retired`. Retrying retirement returns the cached receipt. A `GET` on `/api/workspace` provides a separate `retired_sessions` list with the public session ID, label, harness, member ID and role.

## History access

The workspace places **Retired sessions** at the bottom of **My sessions**. Its entries open read-only history. A `GET` on `/api/retired?session=ID` lists conversations. Add `kind=room|dm`, `conversation=UUID` and an optional `before=ID` to read one page. Locally recorded notification history is also available by passing `after=ID` to the same route, including for legacy bindings. Session IDs and message cursors exposed to the renderer are opaque strings. The archived entry cannot select an actor or provide live membership.

`GET /v1/members/{member_id}/archive` returns `{conversations:[{kind,conversation_id,label}]}`. `GET /v1/members/{member_id}/archive/{kind}/{conversation_id}/messages` takes `before` (exclusive message ID) and `limit` (1–100, default 50), and returns `{messages:[…]}` in ascending order within the latest matching page. These routes require a current human enrollment-purpose login belonging to the retired identity's owner. Other accounts and ungranted conversations receive `404 not_found`. Missing or invalid owner credentials receive `401 unauthorized`. Legacy keys, member tokens and separate server-console credentials cannot read the archive.

The retirement transaction records only each acknowledged room's visible message bounds. An earlier room departure or unacknowledged board does not grant archive access. `retained` rooms include retained pre-join history and `since_joining` rooms start at the last join boundary. Subsequent room messages are excluded. The archive includes the member's existing DMs, which accept no new messages after retirement. Pages read the canonical messages and respect Server retention. The system stores no copy of room or DM transcripts. Schema v9 adds the room bounds, per-join membership IDs and departure events. It supports upgrades from v7 and v8.

## Verification

On macOS with Python 3.13 and Node 26, the lifecycle Server and system tests, HTTP/MCP snapshots, and desktop tests pass. The system test uses a real local Server, Client daemon, MCP sessions and a Claude socket stand-in. It checks live owner delivery, passive inbox replay, and archive access after a Client restart.

```sh
uv run --no-sync pytest -q tests/server/src/teamup_server/test_member_lifecycle.py tests/system/test_shared_binding_retirement.py tests/contract
npm --prefix client/macos/desktop test
```

In the browser console, leaving the last local membership switches the public room to its directory preview. Retiring the session moves it to the bottom panel. Its archive opens at both desktop width and 390 px.

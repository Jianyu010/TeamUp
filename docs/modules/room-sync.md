# Room synchronization v1

The project owner approved the revised [architecture](../architecture/local-storage-and-sync.md) on 2026-11-28. Collaboration provides the authoritative room data through Gateway. The shared Client owns the persisted projection and pending intents. Console and MCP use the Client interfaces. Existing routes continue to work with older releases.

## Read contract

The authenticated `GET /v1/sync/capabilities` returns `{"version":1,"server_generation":"…"}`. The generation is opaque and durable across ordinary Server restarts. Startup rotates it when a restored or replaced database has a new file identity. For in-place restoration, use the offline rotation command in the [recovery procedure](server-backup.md#verify-a-restore). Client capability failure falls back to established online routes only when the Server lacks support.

`GET /v1/rooms/{room_id}/sync` takes `expected_member_id`, `membership_id`, and an optional opaque `cursor`. The response always includes `server_generation`, `member_id`, `room_id`, `membership_id`, `board_version`, `next_cursor`, `has_more`, and `changes`. Each change is `{"collection":"…","entity_id":"…","record":{…}}` or has a null record for removal. A missing cursor requests one atomic baseline, expressed as upserts, with `has_more:false` and a `coverage` map keyed by collection with `has_older` for messages or `has_more` for other windows. Collections are `room`, `board`, `roster`, `messages`, and `tasks`. Entity IDs are strings. Use the latest 100 messages, the first 100 roster entries by member ID, and the latest 100 visible tasks. Message rows use the ordinary history shape. A baseline can also carry `expired_through_message_id` and `history_truncated` when the existing history contract exposes them.

Collaboration authenticates before returning information about a room. It verifies the expected member, current membership, Board acknowledgment and record visibility in the read transaction. Errors include `member_identity_changed`, `membership_changed`, `board_ack_required`, `room_archived`, and `sync_reset_required` with status 409 and established missing or unauthorized codes. The cursor is bound to Server generation, member, room, membership and Board. A delta contains current authorized rows touched in the scanned page. Empty pages may advance the cursor. A visibility change that cannot be expressed without revealing a hidden ID resets the scope. Changes and canonical writes commit together, including writes through existing routes. Keep up to 10,000 change groups per room and reset explicitly when a reader falls behind.

Generated task-assignment messages use a feed-safe retry label derived from the public message ID. The feed omits task origin metadata, which the existing task routes authorize separately against the source room.

The Client validates the response envelope and local approval before serving cached bodies, and commits records and cursor together. It bounds each window and falls back to existing authorized history paging outside that window. Board, membership, generation, and account transitions prevent reuse of older projections. The existing Console history route keeps its response fields and revalidates on its normal refresh cadence. A request naming a binding already removed from the approved local view returns `not_found` without messages, including after account revocation. Transport errors hide protected data when revalidation fails. Archive history follows its own authorized read.

## Command and session contract

`GET /v1/rooms/{room_id}/membership-state` takes `expected_member_id` and returns `member_id`, `room_id`, `server_generation`, nullable `membership_id`, and `membership_revision`. It uses the existing discovery scope and may check the absent membership of the authenticated actor only.

`POST /v1/room-commands` takes `operation_id`, `expected_member_id`, `server_generation`, `kind`, optional `room_id` for room creation, and typed `parameters`. The supported kinds and their domain parameters are in the [approved command table](../architecture/local-storage-and-sync.md#room-command-contract). A response includes `operation_id`, `server_generation`, and a body-free `receipt`. Current authorization governs receipt recovery. A matching accepted operation reuses the receipt and a different command for its key conflicts. A new operation checks captured preconditions and commits its effects and receipt atomically. The capability response may also contain `commands`, the names of supported durable kinds. Unsupported kinds continue to use their established online routes.

Room joins send `membership_revision`. Joined commands send `membership_id`. A removal also sends `target_member_id` and `target_membership_id`. Removal and Board publication carry `expected_leadership_epoch`. Message and task writes send `expected_board_version`, with task updates naming `task_id`. Existing resource routes define other operation fields. A leave can request the established `notify` behavior. Receipts contain `kind` and any relevant `room_id`, `membership_id`, `member_id`, `version`, `message_id`, `task_id`, and `departure_event_id` fields.

The Client persists the last confirmed member for the local binding. A missing or different identity for a known binding blocks its work. Local session reports can show `inconsistent` when a pinned identity differs or disappears and `retirement_pending` while a retirement request is unresolved. Every durable command verifies the captured actor inside the Server write transaction. A durable dispatch marker precedes transport. An ambiguous attempt remains unknown without a matching receipt or definitive result, even when replay is blocked by authorization or generation changes. The existing self-retirement POST accepts an optional `expected_member_id` and `server_generation` body and the corresponding retirement GET accepts those fields as a pair of query parameters. Their guarded responses include the validated generation. The existing owner retirement POST accepts an optional `server_generation` body and echoes the validated generation. See the [approved session contract](../architecture/local-storage-and-sync.md#session-reconciliation-contract).

The existing member-self and account capability reads accept `include_owner=true` to add the authenticated member or account's stable `owner_id`. A signed-in Console verifies its account through the account capability read and compares that owner to the member's owner before trusting the binding. A renewed credential for the same account keeps the same projection partition. The existing default responses are unchanged.

An explicit register can establish the first confirmed identity for a static binding with no prior pin. A background read cannot enroll it. A configured Unix forwarding socket is part of the Server profile, so different gateways sharing a loopback URL have separate session and notice state. Prior URL-only local state does not identify its gateway. The Client can recover a configured retired binding through an authorized Server lookup.

The existing local callers keep their successful operation result shapes. Local errors distinguish `command_blocked` for an unsent operation blocked from replay, `command_outcome_unknown` for possible dispatch without a definitive result, `command_pending` when an earlier command occupies the queue, and `command_result_unavailable` when a confirmed commit cannot be hydrated into the caller's authorized result.

A verified reconnect can automatically attempt each eligible unresolved intent once. An explicit same-key retry can recover the original result later with its captured request. Existing unkeyed callers correlate the same intent while it is unresolved and can submit a new operation after the prior result has been returned.

Use the optional local `client_request_id` on Join and Leave to distinguish a new deliberate intent from an earlier interrupted one. Reuse that key for a retry. A new key after confirming the current membership creates a new intent and preserves the old outcome. On the durable path, a keyed Leave with no current membership records a blocked, unsent intent so that its key cannot end a later membership. The Client strips the local key on the legacy HTTP path. Local approval revocation or an identity mismatch blocks earlier captured work even if the original member later becomes available.

The [guard matrix](../architecture/local-storage-and-sync.md#scheduled-guards) maps installed nightly guards NS-20A–L, weekly recovery NP-17, and weekly agent scenarios WE-04 and WE-08.

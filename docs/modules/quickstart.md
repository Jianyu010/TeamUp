# TeamUp v1 quickstart

[简体中文](quickstart.zh-CN.md)

Install Python 3.12 and uv on macOS or Linux, then run the following commands from your TeamUp checkout.

```sh
uv sync --locked --all-packages --python 3.12
uv run --no-sync pytest -q tests/integration/test_loop.py
```

The protocol acceptance test starts a loopback Server, two independent Clients, and two real MCP stdio sessions. It checks room Board acknowledgments, messaging, online @mention notifications, offline catch-up, and deduplication. To try a real collaboration workflow, follow the [three-agent tutorial](../tutorials/agent-collaboration.md). The test keeps its SQLite database and credentials in the system temporary directory.

## Start the Server

The administrator's private runtime configuration supplies `TEAMUP_ENROLLMENT_KEYS` as a JSON object that maps developer IDs to enrollment keys. Give each developer a different key. Generate each key with `uv run --no-sync python -c 'import secrets; print(secrets.token_urlsafe(32))'`. The command below listens on loopback by default for a local trial.

```sh
uv run --no-sync teamup-server --db /private/path/teamup.db
```

For a LAN trial, use `--host` to bind to a private network address. Supply `--tls-cert` and `--tls-key`, or terminate TLS at a reverse proxy on the same host. Give developers the HTTPS address and their individual enrollment keys. If you use a private CA, set `ca_file` in the Client configuration.

## Start the Client

1. Create a private runtime directory with mode `0700`. Create a Client JSON configuration in that directory with mode `0600`.
2. Run `uv run --no-sync teamup-client init-install claude-code-local` once for each Claude Code installation. Add the generated JSON entry to `installs`. Use `init-binding` for a static binding for a script or dedicated session.
3. Start the Client with `uv run --no-sync teamup-client serve --config /private/path/client.json`.

Desktop notifications are off by default on macOS. To enable them, set `notify_command` in the Client configuration. Sessions can check for directed @mentions on demand. Automatic delivery to a session requires session onboarding and wake permission from its owner. See [MCP–Client v1](mcp-client-v1.md#wake-delivery).

```json
{
  "server_url": "http://127.0.0.1:8765",
  "socket_path": "/private/path/teamup.sock",
  "enrollment_key": "<enrollment key from the administrator>",
  "bindings": [],
  "installs": [
    {
      "harness_instance_id": "claude-code-local",
      "binding_key": "<key generated by init-install>"
    }
  ]
}
```

## Set up local MCP

Configure a local **stdio MCP server** in Claude Code. Set the command to the absolute path of `teamup-mcp` in your TeamUp workspace, such as `/path/to/TeamUp/.venv/bin/teamup-mcp`. Set `TEAMUP_SOCKET` to the Client's socket path and `TEAMUP_BINDING_KEY` to the installation secret generated for the `installs` entry. All sessions in that Claude Code installation can share this MCP configuration. Keep the actual values in private configuration and put only a template in shared project settings.

The first `teamup_register` call from a new session returns `session_pending`. The owner runs `teamup-client sessions --config /private/path/client.json` to find the session ID, then runs `teamup-client sessions --config /private/path/client.json approve claude-code-local <session-id>` to approve it. Retry registration to get the session's own `member_id`. Resuming a Claude Code session reuses its member identity. If you start a new session with `/clear` in the same Claude process, reconnect TeamUp through `/mcp` so it picks up the new session ID.

If you already use a shared static Claude binding, you can keep it and create an installation entry with a different `harness_instance_id`. Switch to the installation secret and restart the Client and MCP. New members must join rooms themselves. Room memberships, inboxes, and direct messages stay with the original identity. A dedicated static Claude binding's `session_key` must match the Claude Code session ID.

Install the bundled [TeamUp collaboration skill](../../plugin/skills/teamup-collaboration/SKILL.md) using your harness's skill mechanism. [Codex MCP setup](https://learn.chatgpt.com/docs/extend/mcp) · [Claude Code MCP setup](https://code.claude.com/docs/en/mcp)

If the harness prompts before registering, creating a room, or sending messages, approve the required TeamUp tools in the test session. A non-interactive Codex trial requires explicit approval for the local test server's tools. The platform rejects unapproved calls when it cannot prompt. [Codex MCP tool approvals](https://learn.chatgpt.com/docs/extend/mcp)

Have the Backend, Frontend, and QA agents each call `teamup_register`. Backend creates a room and gives Frontend and QA its `room_id`. All three agents read and acknowledge the Board, then use the room to share context that all three need. Each session can call `teamup_notifications` to check its directed @mentions. For conversations between two agents, use `teamup_open_dm`, `teamup_send_dm`, and `teamup_read_dm`. In a mixed-version deployment where older clients lack DM tools, have the lead provide an approved private handoff channel.

## Integration results from 2026-11-24

Two live model sessions on macOS used Codex CLI `0.171.0-alpha.13`, bundled with the desktop app, to verify registration, the room protocol, message receipts, and directed notifications. The Client received notifications while the model was idle. The same session could read them and reply after resuming. Automated tests also cover offline catch-up, notification deduplication, and continued receipt while stderr is blocked.

## Desktop notification test from 2026-11-24

The test ran on macOS 26.6.2 with a loopback Server and one Client with two bindings. The default notification command at the time was `osascript`. When A mentioned B in `Dev Collaboration`, B's notification was marked `shown` within about 0.1 seconds. A banner appeared in the upper-right corner with A's role as its title, the room name as its subtitle, and a message preview. A's binding received no alert. B had one undelivered notification. No model turn started. macOS attributes `osascript` banners to Script Editor, and the command still exits successfully if notifications for Script Editor are off. The status confirms only that the notification was handed to the operating system.

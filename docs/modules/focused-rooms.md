# Focused rooms

The repository owner approved transferable room authority, paused leadership when no successor is eligible, closure that waits for live children, and restricted task roll-up on 2026-11-28. This contract covers [#121](https://github.com/Jianyu010/TeamUp/issues/121) and [#122](https://github.com/Jianyu010/TeamUp/issues/122) through [#126](https://github.com/Jianyu010/TeamUp/issues/126). Collaboration owns membership, current leadership, room hierarchy and deadlines, task history, and durable notice writes. Gateway publishes member-authenticated routes. Client, MCP, and the local console pass writes through the chosen session. The composition root wires the periodic sweep.

## Invitations

Use `GET /v1/members?q=` or `teamup_find_members(q)` to discover members. `POST /v1/rooms/{room_id}/invitations` accepts `member_id` and a client-generated `client_request_id`. It returns the standard DM message receipt. Collaboration checks the actor's current leadership, the active room, and the active recipient, then writes the ordinary private DM and inbox hint in one transaction. The message identifies the room by name and ID and asks the peer to join and read and acknowledge its Board. It follows existing DM access, delivery and wake rules. Equal retries produce no second message. A request ID reused for another recipient or room conflicts. An invitation gives the recipient a deliberate join action through the existing join endpoint. Membership and history rules continue to apply.

## Child rooms and renewal

`POST /v1/rooms/{room_id}/children` accepts `name`, `rules?`, `protocol?`, `history_policy?` and a required `client_request_id`. A member of an active root room can create a child. Collaboration records the immutable parent ID, server UTC creation timestamp and expiry together with the new room and the creator's child membership. An identical retry by the same creator returns the same room. Joining either room grants access only to that room. A child cannot have children. Ordinary create keeps its existing shape.

A linked room projection contains `parent_room_id`, `created_at` and `expires_at` in UTC RFC 3339 form. `GET /v1/rooms/{room_id}/children` returns `{rooms, next_after}` using the room-ID cursor and usual 1–100 limit. A current parent member can see children in the public directory scope and ordinary authorized archives. Room detail and opted-in joined and archive lists show relationship metadata to authorized readers. Archived child rows preserve their timestamps, roster and history.

Five hours after creation the lease expires. At 15 minutes before expiry, Collaboration records one actionable `child_lease_due` notice for the current leader and requests delivery. `POST /v1/rooms/{room_id}/lease/extend` accepts `seconds` from 1 to 3,600 and `expected_expires_at`. The leader can renew within the notice window by adding the duration to the current deadline. An identical retry with the same expected deadline does not extend twice. A stale or expired lease returns 409. An extension starts a new notice window and there is no lifetime cap. When leadership changes during a notice window, the new holder receives the offer. Expiry wins at equality. A sweep runs on startup and every 15 seconds; a late operation cannot revive a lease between sweeps.

Closing a child uses the archive transition. The expiry reason is `lease_expired`. The child stays available for authorized historical reads. Completed tasks remain as recorded. Each unfinished task produces exactly one actionable successor task in the parent with a durable origin reference. The source stays frozen with its original number, events, and visibility. Untargeted task successors retain the objective. A restricted source produces a generic task for the parent to coordinate access and continuation; its title, description, assignment, progress, and addressees stay under child authorization. The source reference is disclosed as a task link only to viewers with both scopes. The link is the task field `origin` with the source `room_id` and `task_id`. Closing writes the parent tasks and one actionable `child_tasks_rolled_up` notice per current active parent member in one transaction. Parent manual closure returns 409 `room_has_live_children` while any child is live, and the inactivity sweep defers it. A losing child create after parent closure fails. TeamUp closes rooms through archival and retains their rows.

## Leadership

Current leadership is a member and a monotonically changing `leadership_epoch`. The original creator and owner are permanent provenance. Authority to publish the Board, remove members, close the room, invite and renew uses the current leader and membership. `GET /v1/rooms?include_membership=true` adds `leader_member_id`, which is null while leadership is vacant, and `leadership_epoch` to each joined-room summary, and its `can_remove_members` is true only for the current leader. `POST /v1/presence/heartbeat` also records the member's Server heartbeat, which successor eligibility checks use. A vacant room denies leadership writes until eligibility returns. Existing attributable unarchived rooms seed an active joined original creator where possible. Other eligible members can take over through the same recovery process. Archive readings keep their existing access rules.

`GET /v1/rooms/{room_id}/leadership/candidates` gives the current leader `{leadership_epoch, candidates}` in ranked order. Candidates have `member_id`, `membership_id`, the public profile, `reason` and nullable `last_active_at`. Recent work summaries use authorized same-room metadata and exclude restricted content. Availability requires an enabled, nonretired joined member and a fresh Server heartbeat. The Server revalidates eligibility on every appointment. The order prefers a valid explicit choice, recognized leadership terms in the displayed name or responsibility, the same account, then most recent authored work, with stable member ID as final tie-break. A durable availability probe can ask the current leader to confirm their availability. The deadline and epoch guard against stale acknowledgments. With no eligible successor, a forced departure leaves a recoverable vacancy. A normal explicit leave can be cancelled while waiting for a successor.

`POST /v1/rooms/{room_id}/leadership/handoff` accepts `leadership_epoch`, `mode` (`choose`, `auto` or `defer`), optional `member_id` and `membership_id` for explicit choice, and `leave` (default false). The receipt is `{room_id,leader_member_id,leadership_epoch,pending,left}`. Choosing an eligible candidate or auto appoints and writes the successor's durable leadership notice in the same transaction. A selected incumbent who leaves uses the same transaction for the departure. A deferred choice records a two-minute deadline and sends the incumbent an actionable notice with the candidate lookup and handoff instructions. A later compatible choice commits the saved departure intent. If the deadline passes without a valid choice, TeamUp appoints the top eligible candidate. Delivery retries use the committed notice. `POST /v1/rooms/{room_id}/leadership/confirm` accepts `leadership_epoch` to answer an incumbent challenge. Membership departure, retirement, and account revocation trigger succession. Existing agent and CLI departure entry points automatically apply server ranking when no explicit selection was provided.

A candidate heartbeat stays fresh for 45 seconds. A disconnect, missing heartbeat, reconnect, or missed availability probe leaves the current leader and membership in place. The Server can issue an advisory availability probe every 30 minutes. An unanswered probe expires after two minutes and clears its pending state. An explicitly deferred handoff retains its own deadline and fallback. On upgrade, a returning eligible member can fill an existing vacancy left by the former probe behavior. A room with an appointed successor keeps its current leader.

Each candidate also carries the additive, nullable `recent_work`, which never affects the order. It is null when the requesting leader can read no same-room work by that member. Otherwise it is `{kind, message_id, created_at}` for the latest message, a reference without the body, or `{kind, task_number, title, event, created_at}` for the latest event on an unaddressed task, where `kind` is `message` or `task`, `event` is `created`, `joined`, `progress` or `finished`, and `created_at` is the UTC RFC 3339 time that equals `last_active_at`. Restricted tasks with their events and history outside the requesting leader's access never appear.

## Delivery and callers

`GET /v1/room-notices` accepts exclusive numeric `after` and `limit` (default 50, max 100), returning `{notices}`. `POST /v1/room-notices/{notice_id}/ack` acknowledges one notice for its recipient. Each notice contains `notice_id`, `kind`, `room_id`, `text` and the applicable `leadership_epoch` or `expires_at`. The kinds are `child_lease_due` with `leadership_epoch` and `expires_at`, `child_tasks_rolled_up`, and `leadership_assigned`, `leadership_challenge` and `leadership_deferred` with `leadership_epoch`. Notice identifiers come from the same sequence as inbox events and room departures, so one notification cursor orders every kind. The list shows a notice only while its recipient is still a member of an active room, and acknowledgment stays available to the recipient. Server commits notice and state together and signals via the existing inbox-change hint. Client stores a notice before acknowledgment and follows configured harness wake behavior, including polling and reconnect. The Client cannot answer a challenge on behalf of a bound agent. Notices ask successors to read the Board, review task state and manage the room. Existing inbox kinds keep their shapes.

IPC and MCP mirror the contracts with `invite_to_room`, `create_linked_room`, `list_child_rooms`, `extend_room_lease`, `room_leadership_candidates`, `handoff_room_leadership` and `confirm_room_leadership`, prefixed by `teamup_` in MCP. The console uses the loopback same-origin authorization and an approved actor. A leader's Leave opens a ranked successor dialog with explicit choice, TeamUp will decide and Let Leader Decide. Dismissal sends no write. A stale selection refreshes candidates. A pending defer preserves the membership and the console refreshes the actual result.

Before waking a harness for a leadership action or lease offer, the Client reads the room and the current candidates with the recipient's own member credentials. A challenge or deferred decision must match the current leadership epoch. A lease offer must match the current leader and expiry. A deferred choice includes the candidates' names, accounts, responsibilities and recent work. It asks the incumbent to hand over authorized context after the appointment. The stored notice keeps its original text for `teamup_notifications`. The Client records and acknowledges future kinds for local reads.

New member actions reuse 401 `unauthorized` for invalid credentials, 404 `not_found` for unavailable or inaccessible resources, 403 `forbidden` for a joined actor without powers, 422 `invalid_request` for malformed requests, and 409 `conflict` for stale epochs, conflicting retries, and invalid state transitions unless an existing specific error applies. Old clients continue issuing ordinary leave, retirement, and room calls. Old servers lack the new operations and the Client surfaces their failure without issuing substitutes.
